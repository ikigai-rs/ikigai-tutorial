# A live page over HTTP

[Composites, one layer at a time](composites.md) ended with `page.html`, a saved answer.
[Naming a composition](naming.md) removed copies between layers. This chapter puts the
Quakes notes composite behind the CLI's HTTP door: the browser asks for the page, and the
kernel reads its sources. Edit a note, reload, and the page changes without restarting the
server. No Rust is needed.

## 1. A config home of your own

Use a shell in `~/quakes`, with the recorded `quakes-2024-01-01.geojson` downloaded in
[A week of earthquakes](index.md#what-you-need). Quit any earlier REPL. These steps make
`quakes-http` inside that directory: your own config home, with its own `config.toml`,
`names`, and `ws/` file workspace. They do not use your usual CLI configuration.

Install `ikigai-cli` {{#include ../../ikigai-cli.version}} with its optional `web` feature
if your installation lacks HTTP support:
`cargo install ikigai-cli --locked --version '={{#include ../../ikigai-cli.version}}' --features web`.
The book's transcript runner installs that build before replaying every `$` line below.
File listings are written into the scratch config home by the same check. The recorded
week makes the answers repeatable; no live feed is fetched here.

<!-- transcripts: workspace crates/quakes/quakes-2024-01-01.geojson -->
<!-- transcripts: normalize workdir -->

<!-- transcript: run; exit 0 -->

```console
$ mkdir -m 700 quakes-http
$ mkdir -m 700 quakes-http/ws
$ cp quakes-2024-01-01.geojson quakes-http/ws/week.geojson
```

Save this as `quakes-http/config.toml`. Relative `files` paths resolve from the config home,
so the REPL and HTTP server will both read `quakes-http/ws`:

<!-- transcript: file quakes-http/config.toml -->

```toml
files = "ws"
```

## 2. The recorded selection and your live notes

Keep the earthquakes of magnitude 6 and up, with the id, magnitude and place the notes view
needs. This is the JSON equivalent of the notable-earthquakes selection in
[Composites](composites.md#6-at-a-shell-your-own-notes), over just the first week:

<!-- transcript: run; exit 0 -->

```console
$ ikigai --config-home "$PWD/quakes-http" --quiet -c 'source urn:json:query src=urn:file:week.geojson q=".features | map(select(.properties.mag >= 6) | {id: .id, mag: .properties.mag, place: .properties.place}) | sort_by(.mag) | reverse" | sink urn:file:notable.json'
wrote 145 bytes to notable.json
[1 computed · 1 uncacheable]
```

This selection is a saved input. The HTTP door has a smaller set of resources than the REPL:
it binds the function library and files, but not `urn:json:query` or SPARQL. The selection
is therefore prepared once in the REPL. Changing `week.geojson` later requires rerunning
this command; its query dependencies do not cross into the server. The live composite
below starts at `notable.json`, its row template, and the note files, all read by the
server itself. Editing any of those sources reaches its page through golden threads.

Write one note, and the fallback for an earthquake with no note yet:

<!-- transcript: run; exit 0 -->

```console
$ mkdir -m 700 quakes-http/ws/notes
$ printf '%s' 'Felt in Kanazawa.' > quakes-http/ws/notes/us6000m0xl.txt
$ printf '%s' 'no note yet' > quakes-http/ws/notes/none.txt
```

Save this row template as `quakes-http/ws/row.html`, using the same per-earthquake file
lookup and fallback as Composites. `$h{…}` escapes text for HTML:

<!-- transcript: file quakes-http/ws/row.html -->

```html
<li>M$h{{mag}} $h{{place}}: $h{urn:file:notes/{id}.txt || urn:file:notes/none.txt}</li>
```

Save the page template as `quakes-http/ws/page.html`. The rows are HTML generated by your
row template, so `$r{…}` splices them as markup:

<!-- transcript: file quakes-http/ws/page.html -->

```html
<!doctype html>
<html lang="en">
<head><meta charset="utf-8"><meta name="viewport" content="width=device-width"><title>Quakes</title></head>
<body><main><h1>A recorded week of earthquakes</h1>
<ul>$r{urn:quakes:rows}</ul>
</main></body>
</html>
```

Save these bindings as `quakes-http/names`, in the format `bind` wrote in
[Naming a composition](naming.md). The first fills one row per earthquake; the second
fills the page, reading the rows by name:

<!-- urn-gate: unbound urn:quakes:rows — the reader binds these rows in their own config home's names file, replayed by the console runner. -->
<!-- urn-gate: unbound urn:quakes:page — the reader binds this page in their own config home's names file, replayed by the console runner. -->

<!-- transcript: file quakes-http/names -->

```text
urn:quakes:rows = source urn:iki:fn:each src=urn:file:notable.json template=urn:file:row.html
urn:quakes:page = source urn:iki:fn:compose src=<urn:file:page.html>
```

`src=<…>` reads the page template by reference. `urn:iki:fn:each` reads its list and template
through the kernel too, and each filled row reads its note. No filled row or page is saved
between these layers.

## 3. Give the page an HTTP address

Save this route table as `quakes-http/ws/routes.json`:

<!-- transcript: file quakes-http/ws/routes.json -->

```json
{"routes":[{"match":"/quakes","target":"urn:quakes:page"}]}
```

Start the server in this terminal. The small shell wrapper saves its process ID, then replaces
itself with `ikigai`, so the saved ID is the server's. Port `0` asks the operating system for a
free TCP port on loopback. Use the port your banner prints in the later commands; `51234` below
is an example (the check substitutes the actual port too). No Unix socket is needed.

<!-- transcript: serve; normalize port -->

```console
$ sh -c 'echo $$ > quakes-http/server.pid; exec ikigai --config-home "$PWD/quakes-http" serve --http 0 --names "$PWD/quakes-http/names" --routes urn:file:routes.json --routes-only --cap "urn:cap:fs:read:$PWD/quakes-http/ws"'
ikigai: mount   none composed — no `mount` lines in the config home
ikigai: watching $PWD/quakes-http/ws (a file changed on disk is served fresh)
ikigai: serving HTTP on 127.0.0.1:51234  (fixed ceiling: urn:cap:fs:read:$PWD/quakes-http/ws; 1 route(s) from urn:file:routes.json, watching, routes-only (un-routed → 404), names from $PWD/quakes-http/names; …)  (Ctrl-C to stop)
```

`--names` is explicit on the HTTP door: without it, the server does not read the config home's
names file. Both bindings resolve inside this server, so their dependencies stay in its
kernel. The fixed capability ceiling grants read access to this workspace; it grants no
file writes or network access. `--routes-only` makes paths outside the table return 404.
This is a local walkthrough; leave the loopback address and CORS defaults in place. The
ellipsis in the banner stands for its other policy details, including rate limits and uploads.

In a second shell in `~/quakes`, ask for the page:

<!-- transcript: run; exit 0 -->

```console
$ curl -fsS http://127.0.0.1:51234/quakes
<!doctype html>
<html lang="en">
<head><meta charset="utf-8"><meta name="viewport" content="width=device-width"><title>Quakes</title></head>
<body><main><h1>A recorded week of earthquakes</h1>
<ul><li>M7.5 2024 Noto Peninsula, Japan Earthquake: Felt in Kanazawa.</li>
<li>M6.2 8 km SW of Anamizu, Japan: no note yet</li>
</ul>
</main></body>
</html>
```

Open that same address in your browser. It displays a heading and a list of two earthquakes.
Reload asks the running kernel for the composite again. Check the HTML response type, ask
for the note again, and check a path outside the route table:

<!-- transcript: run; exit 0 -->

```console
$ curl -fsS -o /dev/null -w '%{content_type}\n' http://127.0.0.1:51234/quakes
text/html
$ curl -fsS http://127.0.0.1:51234/quakes | grep 'Felt in Kanazawa'
<ul><li>M7.5 2024 Noto Peninsula, Japan Earthquake: Felt in Kanazawa.</li>
$ curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:51234/not-a-route
404
```

## 4. Edit a source, then reload

Change the note on disk while the same server is running:

<!-- transcript: run; exit 0 -->

```console
$ printf '%s' 'The shelves shook & the lights went out.' > quakes-http/ws/notes/us6000m0xl.txt
```

Reload in the browser: the new note appears. The `&` displays as an ampersand, because the
row template escapes it as `&amp;`. File watching is asynchronous. The shell check below
allows up to five seconds for the edit to reach the server, then fails unless the HTTP
answer has the new note:

<!-- transcript: run; exit 0 -->

```console
$ for attempt in $(seq 1 50); do curl -fsS http://127.0.0.1:51234/quakes > quakes-http/latest.html || exit 1; if grep -q 'The shelves shook &amp; the lights went out.' quakes-http/latest.html; then break; fi; sleep 0.1; done; grep 'The shelves shook &amp; the lights went out.' quakes-http/latest.html
<ul><li>M7.5 2024 Noto Peninsula, Japan Earthquake: The shelves shook &amp; the lights went out.</li>
```

The server's file watcher cuts the note's golden thread. The rows and the page that read
it become stale; the next HTTP read recomputes them. `notable.json` has not changed, so its
cached read can still be used. There is no refresh script, restart, or copy of a filled
page to replace. Editing `notable.json`, `row.html`, or `page.html` follows the same
dependency chain; editing the names file rebinds the names on the running door too.

The polling command is only a transcript check for the file watch, not a browser update
mechanism. This page changes **on reload**, not automatically while you look at it. It shows
the recorded week's selection and your current notes, not today's earthquakes. For the
moving feed's freshness rules, see [Somebody else's resource](http.md).

## 5. Stop this server

Use Ctrl-C in the server's terminal, or run this from the second shell. Stop the saved process
ID, never a pattern that could match another reader's server:

<!-- transcript: stop; exit 0 -->

```console
$ kill "$(cat quakes-http/server.pid)"
```

Your config home and source files remain for the next run. The final page is an answer, not
an exported snapshot: starting the same HTTP command again rebuilds it from those sources.
